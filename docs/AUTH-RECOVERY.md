# Reserved security-question and email-OTP recovery

The owner's 2026-10-06 instruction adds reserved security-question and email
verification to **security reset only**. Email OTP remains excluded from login.
This is additive to [account authentication](ACCOUNT-AUTHENTICATION.md): it does
not replace fresh independent identity authentication or an existing
authenticator/recovery-code proof. There is no unauthenticated reset endpoint,
email account lookup, operator-enrollment endpoint, or client-supplied identity.

## User flow and authorization

1. Log in with an enabled, independently provisioned password, registered wallet,
   or hardware CA method. Management authorization expires five minutes after
   that login. A TOTP or saved-recovery-code login cannot manage these factors.
2. In management, reserve an email address and choose a question. Supply an
   answer of at least 12 characters after normalization. If an authenticator is
   already configured, also supply its current code or an unused saved recovery
   code. The email address becomes active only after its emailed code is confirmed.
   Successful enrollment increments the credential revision and revokes every
   session for that account.
3. For later authenticator replacement, answer the reserved question and receive
   an eight-digit OTP at the **stored, verified address**. Confirming it produces
   a short-lived, single-use reset proof. Submit that proof together with the
   existing authenticator/recovery code when starting replacement, then confirm
   a code generated by the new authenticator. All three independent-login,
   existing-credential and reserved-factor requirements remain enforced.
4. To change the reserved email/question/answer, first verify the old reserved
   question and email. Supply that reset proof and the existing authenticator or
   recovery code, when configured, before verifying the proposed new email.
   A new address is never accepted as the recipient of a reset challenge.

An account without reserved factors retains the existing authenticated
replacement process. The UI must show that it has **not** configured reserved
recovery and must not claim that email or question verification took place.
Initial authenticator enrollment is not replacement. Once configured, factors
cannot be silently removed or bypassed by disabling a login method.

Security answers are supplementary knowledge, not independent identity proof.
Do not use publicly discoverable answers or reuse a password. The supported
question identifiers are `recovery-phrase`, `first-school`, and
`childhood-place`; presentation labels are localized by the UI. Prefer a long,
private recovery phrase. Losing all independently authenticated access or the
required existing factors requires the operator's separately authorized identity
recovery process; this implementation does not invent a bypass.

## Same-origin API

Every mutation uses the existing authenticated HttpOnly session, exact configured
Origin/Host/tenant, JSON content type and `X-Wallet-CSRF` checks. All new state is
bound to the server's selected identity, never fields claimed in the request.

- `GET /auth/account` includes `recovery` with `configured`, `emailMasked`,
  `questionId`, `emailOtpAvailable`, and the fixed `questions` list. No full
  email, security answer, hash, OTP, or authorization token is returned here.
- `POST /auth/recovery/enroll/start` accepts `email`, `questionId`, `answer`,
  optional `existingCode`, optional `recovery: true` for a saved code, and
  `resetProof` when replacing existing reserved factors. It returns
  `challengeId`, `expiresAt` (Unix milliseconds), `emailMasked`, and `digits: 8`.
- `POST /auth/recovery/enroll/confirm` accepts `challengeId` and string `code`.
  Success returns `{ configured: true, loggedOut: true }`.
- `POST /auth/recovery/reset/start` accepts `answer`. Recipient and identity
  overrides (`email`, `to`, `username`, `account`, `chainId`, `questionId`) are
  refused. It returns the same challenge metadata and sends only to the stored
  reserved address.
- `POST /auth/recovery/reset/confirm` accepts `challengeId` and string `code`.
  It returns `resetProof` and `expiresAt`. This is not a session or login token.
- `POST /auth/totp/enroll/start` accepts `purpose: "replace"`, `existingCode`,
  optional `recovery: true`, and the `resetProof` for a configured profile. The
  existing new-authenticator confirmation flow is unchanged.
- `POST /auth/recovery/cancel` cancels this session's pending challenges and
  proofs. Its `cancelled` and `confirmationInProgress` fields distinguish a
  queued operation that was cancelled from a store commit already persisting.

The client must keep answers, OTPs and reset proofs only in short-lived memory,
clear inputs promptly, discard stale asynchronous responses, and clear all
recovery state on logout, identity change, expiry and page exit. A dispatched
email or a store commit already linearized cannot be recalled by closing a UI.

## Credential storage, replay and abuse bounds

`server/recovery-service.mjs` stores a versioned `recoveryProfile` alongside the
existing credential fields in the **existing encrypted credential store**.
It contains the verified email, verification time, question identifier, and a
random-salt scrypt answer hash. No plaintext answer or pending OTP is persisted.
Answers use NFKC normalization, trimmed/collapsed whitespace and lowercase; the
result must contain at least 12 characters and at most 512 UTF-8 bytes. Raw
answer input is limited to 1024 bytes before normalization. Hash parameters
match the versioned password helper: N=32768, r=8, p=3, 32-byte output.

- OTPs use cryptographic random eight-digit strings. Only an HMAC-SHA256 digest
  with a random process-only pepper is retained; the digest also covers a random
  salt, challenge ID, origin, tenant, username, selected account/chain, credential
  revision, session ID and `enroll`/`reset` purpose. The pepper is not a credential
  store key and is never persisted or supplied to the browser.
- OTP lifetime is at most five minutes, further capped by independent-login
  freshness. Each challenge permits five failed matching-code attempts.
- Send attempts are bounded to five per account in 15 minutes, with a 60-second
  cooldown per account and purpose. A separate destination digest limits email
  delivery to five in 15 minutes. Security-answer attempts are capped at five
  and OTP verification attempts at ten per account in 15 minutes. Failures count.
  Checking the old reserved address and then verifying a new address can proceed
  immediately because reset and enrollment have separate cooldowns.
- Answer hashing/verification is limited to two simultaneous operations; SMTP
  delivery is independently limited to two. In-memory maps are bounded. These
  are single-process defenses, not distributed abuse prevention.
- Reset proofs are random bearer values returned once, stored only by their
  digest, valid for at most two minutes, and capped by the originating OTP and
  fresh-login deadlines. They bind the same identity/session/revision and exact
  stored recovery profile. They are consumed synchronously inside the serialized
  existing-credential transaction **after** a correct old credential matches.
  An invalid old code cannot consume a valid reset proof.
- OTP confirmation is claimed synchronously before asynchronous store reads.
  Concurrent confirmation, duplicate proof consumption, logout/cancel while
  queued, changed credential revision, expiry and clock reversal fail closed.
  A write already in persistence may finish; account sessions are then revoked.
- Pending challenges, proof grants and their digest pepper die on restart.
  Stored credential/profile revisions and TOTP/recovery replay counters retain
  the existing encrypted-store guarantees. Never restore an older credential
  snapshot as a routine rollback; that can revive consumed existing factors.
- Recovery endpoints require authentication before inspecting an account's
  profile. Wrong/missing answer or invalid OTP/proof failures use `AUTH_REFUSED`;
  no public email/account lookup is introduced. Malformed persisted profiles
  fail closed rather than being treated as unenrolled.

## Mail task integration, no service activation

`server/mail-otp.mjs` supplies a real bounded SMTP submission adapter, mounted
by `server/main.mjs`. The existing separately authorized mail task/operator must
provide all three runtime inputs through its approved secret/configuration
mechanism:

- `WALLET_AUTH_SMTP_PORT`: its explicitly configured **implicit-TLS SMTP
  submission** port. There is no guessed runtime port or plaintext fallback;
  port 443 is refused, preserving the repository's SSH reservation.
- `WALLET_AUTH_SMTP_USERNAME`: existing authorized SMTP account identifier.
- `WALLET_AUTH_SMTP_PASSWORD`: existing SMTP secret, supplied at runtime and
  never entered into the page, source, command-line arguments, logs or artifacts.

The destination host is fixed to `mail.8415wallet.com` and the envelope/header
sender to `noreply@8415wallet.com`. The sender connects only when an authorized
enrollment/reset request actually needs mail; constructing it does not connect.
All three environment inputs absent means email recovery is unavailable. Partial
or invalid configuration refuses startup. No change to the existing auth JSON
schema or credential-store encryption key is required.

The transport uses implicit TLS with TLS 1.2 or later, normal certificate-chain
and hostname validation, and AUTH PLAIN only after verified TLS. It requires the
configured server to advertise AUTH PLAIN. There is no STARTTLS downgrade,
unencrypted relay, alternate host, unverified certificate or unauthenticated
fallback. A deployment offering only STARTTLS must arrange an explicitly approved
implicit-TLS submission endpoint; do not silently change TLS mode or ports.
ASCII mailbox syntax is deliberately bounded; quoted local parts, SMTPUTF8 and
arbitrary headers/HTML/attachments are unsupported.

SMTP replies, total response bytes, concurrency and the complete transaction's
timeout are bounded. Failures expose only `AUTH_EMAIL_UNAVAILABLE`. There is no
automatic retry after DATA: a lost acknowledgement may mean mail was accepted,
so retrying could duplicate delivery. A successful SMTP acceptance is not proof
of inbox delivery. The email contains only its purpose, code, expiry, tenant and
request origin; it contains no security answer, password, wallet secret or
transaction approval. Provider logs and the user's mailbox still require their
own operational security controls.

The production mailbox, DNS, TLS certificate, outbound delivery and spam policy
remain the separate mail task's responsibility and require explicit acceptance.
This change does not provision a service, transmit actual email, create credentials,
change a store key, deploy, or claim production/physical-device security acceptance.

## Local verification

`node --test tests/auth-recovery.test.ts` exercises synthetic factor enrollment,
fresh independent/current-code requirements, hashed-answer and encrypted-store
persistence, recipient substitution refusal, question checks, expiry, rate
limits, replay/concurrency, cancellation before/during commit, unavailable mail,
and SMTP command handling through an injected **in-memory fake transport**.
It also runs the real HTTP auth service on ephemeral loopback with synthetic
wallet signers, proving CSRF/origin/tenant binding, all-factor TOTP replacement,
profile preservation and proof invalidation after login-method changes.
No SMTP test connects to the production hostname or sends a real email.

Run the broader authentication, typecheck, browser, release/package and existing
wallet regression suites as well. Focused synthetic results are not a security
audit or production delivery evidence.

Primary references: [RFC 8314](https://www.rfc-editor.org/rfc/rfc8314),
[RFC 4954](https://www.rfc-editor.org/rfc/rfc4954), and the
[Node TLS API](https://nodejs.org/api/tls.html).

## Registration identity alignment

Email ownership verification is also used in the separate ordinary-registration
flow described in [EMAIL-REGISTRATION.md](EMAIL-REGISTRATION.md). Its OTP purpose,
preauthentication binding and challenge state are distinct from recovery. It
cannot satisfy a reset challenge or log a user in alone. Once registration is
complete, the reserved recovery email must equal the verified account email.
Changing it uses the protected account-email migration API, which verifies the
new address and atomically updates both the directory and existing recovery
profile; recovery enrollment cannot redirect messages to a different address.
